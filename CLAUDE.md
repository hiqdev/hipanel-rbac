# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run tests (from the repo root):
```sh
../../../vendor/bin/phpunit -c phpunit.xml.dist
```

Run a single test:
```sh
../../../vendor/bin/phpunit -c phpunit.xml.dist --filter testClient
```

After editing `src/files/source/tree.php`, regenerate the compiled store and metadata:
```sh
./vendor/bin/hidev rbac/reinit
```

This regenerates `src/files/items.php` (the compiled auth store) and updates `src/files/source/metadata.php` with any new role/permission descriptions. Run tests after to verify.

## Architecture

### Source vs. compiled

The hierarchy is maintained in two source files under `src/files/source/`:
- `tree.php` — the role/permission DAG (the only file you should edit to add/remove roles and permissions)
- `metadata.php` — descriptions and `internal` flags; auto-generated by `rbac/reinit`, but hand-editable for custom flags

`src/files/items.php` is compiled output from those sources. Never edit it directly.

### The staff-* pattern

Base roles (`role:admin`, `role:manager`, `role:support`) contain only **client-safe** permissions. Staff-only permissions live in their `staff-*` counterparts:

| Staff role | Adds on top of base |
|---|---|
| `role:staff-admin` | `role:admin` + `role:server.staff-admin` + `role:hub.staff-admin` + `role:blacklist.manager` |
| `role:staff-manager` | `role:manager` + `role:bill.staff-manager` + `role:installment-plan.manager` + `role:blacklist.manager` |

When adding a permission, decide first: is it client-safe? If not, put it in the `staff-*` role.

### role:client is a superset of admin + manager + support

`role:client` includes `role:support`, `role:admin`, and `role:manager`. A client must always have at least as many permissions as any sub-user they create. When adding a permission to any of those three base roles, also verify it is present in `testClient()` in `tests/unit/CheckAccessTrait.php`.

### The `internal` flag

A permission marked `internal` in `metadata.php` contains staff-only capabilities and should not surface in the public role-assignment UI. `AuthManager::isItemInternal()` propagates this flag upward recursively — if any descendant is internal, the ancestor is too. Notable consequence: `role:client` itself becomes internal because it inherits `order.read` via `role:stock.user`.

### deny: assignments

`deny:permission` items restrict a specific user below their role's defaults. Example: `role:client,deny:server.read` removes server read access from an otherwise-standard client. See `testLimited()` in `tests/unit/CheckAccessTrait.php`.

### AuthManager

`AuthManager` (`src/AuthManager.php`) extends Yii2's `PhpManager`. It overrides `checkAccess()` to also evaluate `deny:*` items, and lazy-loads assignments from the current user identity on first check. Persistent assignments are written only via `persistAssignments()`, not the regular `saveAssignments()` hook.

### Updating tests

`tests/unit/CheckAccessTrait.php` contains exact permission-set assertions per role (`assertAccesses()`). Every change to `tree.php` that affects a role's resolved permission set requires a corresponding update to the relevant `test*()` method. The test helper checks that all listed permissions are granted **and** that every other permission is denied, so both omissions and additions will fail.
